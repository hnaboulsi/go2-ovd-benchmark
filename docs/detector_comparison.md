# Practical detector comparison

| Family | Task and prompt form | Output and integration | Speed, memory, and Apple Silicon | API and license | Likely walking-camera failures | Project role |
|---|---|---|---|---|---|---|
| CLIP | Image or crop classification from class text | Image-text similarity; no native boxes or proposals | Small variants are practical on CPU/MPS | Stable PyTorch API; OpenAI CLIP code is MIT | Background-dominated full frames, crop dependence, view and occlusion sensitivity, prompt ambiguity | Conceptual and future crop-classification baseline, not the primary detector |
| YOLO-World | Open-vocabulary detection from a class list | Boxes, labels, scores; region-text interaction is built into the detector through RepVL-PAN and contrastive training | Designed for high throughput; NVIDIA numbers do not predict M4 throughput; the MMYOLO stack is less direct on MPS | Official MMYOLO/Python path; official code is GPL-3.0 | Motion blur, small distant objects, domain shift, similar class embeddings, confidence flicker | Second adapter when throughput is the priority |
| Grounding DINO Tiny | Open-set detection and phrase grounding from class names or referring expressions | Boxes, phrase labels, scores; tightly integrated text and region features | Tiny is still transformer-heavy but works through PyTorch on CPU and, when supported, MPS | Direct Hugging Face Transformers API; model and implementation are Apache-2.0 | Token/phrase mapping errors, tiny-object misses, distractor confusion, threshold sensitivity, frame-to-frame box jitter | First adapter for Friday |
| OWLv2 | CLIP-derived open-vocabulary object detection from one or more text queries | Query-conditioned boxes and scores; image and text towers are trained for detection with self-training | Transformer baseline is feasible on CPU/MPS but generally slower and heavier than real-time YOLO variants | Direct Hugging Face Transformers API; Apache-2.0 implementation/checkpoints | Similar classes, small objects, clutter, viewpoint changes, prompt formulation, unstable scores | Next clean CLIP-derived detection baseline |
| LocateAnything-3B | Generative/generalist localization from natural-language tasks and expressions | Generated boxes or points through an image-text-to-text model; localization and language generation are tightly coupled | A 3B VLM and high-throughput kernels are excessive for the 16 GB M4 baseline; official performance path emphasizes Linux/NVIDIA | Transformers/custom-code path; NVIDIA non-commercial research license for the released weights | Generation/format errors, latency, memory pressure, small-object and motion artifacts, prompt sensitivity | Documented for future NVIDIA deployment, deferred now |

Primary sources: [YOLO-World CVPR paper](https://openaccess.thecvf.com/content/CVPR2024/html/Cheng_YOLO-World_Real-Time_Open-Vocabulary_Object_Detection_CVPR_2024_paper.html), [YOLO-World official code](https://github.com/AILab-CVC/YOLO-World), [Grounding DINO official code](https://github.com/IDEA-Research/GroundingDINO), [Grounding DINO Transformers documentation](https://huggingface.co/docs/transformers/model_doc/grounding-dino), [OWLv2 paper](https://arxiv.org/abs/2306.09683), [OWLv2 Transformers documentation](https://huggingface.co/docs/transformers/model_doc/owlv2), [OpenAI CLIP](https://openai.com/index/clip/), and [LocateAnything model card](https://huggingface.co/nvidia/LocateAnything-3B/blob/main/README.md).

The practical order is Grounding DINO Tiny first, YOLO-World when throughput becomes central, and OWLv2 as the clean CLIP-derived class-query baseline. Raw CLIP is not a bounding-box detector. LocateAnything is deferred until a Linux/NVIDIA target and its license constraints are acceptable.
